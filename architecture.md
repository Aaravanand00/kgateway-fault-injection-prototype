# Architecture: Gateway-Level Fault Injection

## 1. Architecture Overview

This document describes the architecture of the proposed gateway-level fault injection feature for kgateway. The solution operates at the API gateway layer, leveraging Envoy Proxy's native fault injection capabilities to inject delays and aborts into HTTP traffic without requiring changes to application code.

### High-Level Architecture

The architecture consists of four main layers:

```
┌────────────────────────────────────────────────────────────────┐
│                    CONTROL PLANE                               │
│  ┌──────────────────┐         ┌──────────────────────────┐    │
│  │  Kubernetes API  │         │  kgateway Controller     │    │
│  │  (CRDs)          │◄────────│  • Watch policies        │    │
│  │  • Gateway       │         │  • Translate to Envoy    │    │
│  │  • HTTPRoute     │         │  • Push via xDS          │    │
│  │  • GatewayPolicy │         │                          │    │
│  └──────────────────┘         └──────────────────────────┘    │
└────────────────────────────────────────────────────────────────┘
                                        │
                                        │ xDS Protocol
                                        │ (gRPC)
                                        ▼
┌────────────────────────────────────────────────────────────────┐
│                     DATA PLANE                                 │
│                ┌─────────────────────────────┐                 │
│   Client ─────▶│      Envoy Proxy            │────▶ Backend    │
│                │  • HTTP Fault Filter        │                 │
│                │  • Router Filter            │                 │
│                └─────────────────────────────┘                 │
└────────────────────────────────────────────────────────────────┘
```

**Key principle**: User configuration (GatewayPolicy CRD) is reconciled by the kgateway controller and translated into Envoy filter configuration, which is applied at runtime via the xDS protocol.

## 2. Core Components

### 2.1 Gateway API Resources

The foundation is built on standard Kubernetes Gateway API resources:

#### Gateway
Defines the entry point for traffic. Example:
```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: my-gateway
  namespace: demo
spec:
  gatewayClassName: kgateway
  listeners:
  - name: http
    port: 8080
    protocol: HTTP
```

#### HTTPRoute
Defines routing rules from Gateway to backend services. Example:
```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: my-route
  namespace: demo
spec:
  parentRefs:
  - name: my-gateway
  rules:
  - backendRefs:
    - name: httpbin
      port: 80
```

### 2.2 Fault Injection Policy (New Component)

A custom resource (CRD) that attaches fault injection behavior to a Gateway or HTTPRoute:

```yaml
apiVersion: gateway.kgateway.io/v1
kind: GatewayPolicy
metadata:
  name: fault-injection-demo
  namespace: demo
spec:
  targetRef:
    kind: Gateway
    name: my-gateway
  faultInjection:
    delay:
      fixedDelay: 5s
      percentage: 50.0
    abort:
      httpStatus: 503
      percentage: 10.0
```

**Key fields**:
- `targetRef`: Specifies which Gateway or HTTPRoute to apply the policy to
- `faultInjection.delay`: Configures latency injection
- `faultInjection.abort`: Configures error response injection
- `percentage`: Controls what fraction of requests are affected

### 2.3 kgateway Controller

The controller is responsible for:

1. **Watching** GatewayPolicy resources for changes
2. **Validating** policy configuration (percentages, status codes, durations)
3. **Translating** policy to Envoy's `HTTPFault` filter configuration
4. **Pushing** configuration to Envoy via xDS (Listener Discovery Service)

**Reconciliation Loop**:
```
GatewayPolicy Created/Updated
         │
         ▼
    Validate Policy
         │
         ▼
  Translate to Envoy Filter Config
         │
         ▼
    Generate xDS Snapshot
         │
         ▼
   Push to Envoy via LDS/RDS
         │
         ▼
   Update Policy Status (Ready/Error)
```

### 2.4 Envoy Proxy (Data Plane)

Envoy serves as the actual gateway that processes HTTP traffic. The fault injection feature uses Envoy's built-in `envoy.filters.http.fault` filter.

**Envoy's HTTP Filter Chain**:
```
Request → Fault Injection Filter → Router Filter → Upstream Service
              ↓
         (May inject delay)
              ↓
         (May inject abort)
```

**Envoy Filter Configuration** (generated by controller):
```json
{
  "name": "envoy.filters.http.fault",
  "typed_config": {
    "@type": "type.googleapis.com/envoy.extensions.filters.http.fault.v3.HTTPFault",
    "delay": {
      "fixed_delay": "5s",
      "percentage": {
        "numerator": 50,
        "denominator": "HUNDRED"
      }
    },
    "abort": {
      "http_status": 503,
      "percentage": {
        "numerator": 10,
        "denominator": "HUNDRED"
      }
    }
  }
}
```

## 3. Request Flow

### 3.1 Normal Request Flow (No Fault Injection)

When no fault injection policy is applied:

```
┌────────┐
│ Client │
└───┬────┘
    │ 1. HTTP Request
    ▼
┌─────────────────────────┐
│  Envoy Gateway          │
│                         │
│  [Router Filter]        │◄─── Routes request based on HTTPRoute
│                         │
└───┬─────────────────────┘
    │ 2. Forward to Backend
    ▼
┌─────────────────────────┐
│  Backend Service        │
│  (httpbin)              │
└───┬─────────────────────┘
    │ 3. HTTP Response
    ▼
┌────────┐
│ Client │
└────────┘
```

**Latency**: ~5-50ms (normal network + processing)

---

### 3.2 Request Flow with Delay Injection

When a delay policy is applied (e.g., "inject 5s delay into 50% of requests"):

```
┌────────┐
│ Client │
└───┬────┘
    │ 1. HTTP Request
    ▼
┌─────────────────────────────────────────┐
│  Envoy Gateway                          │
│                                         │
│  [Fault Injection Filter]               │
│   • Random selection (50% chance)       │
│   • If selected: sleep(5s)              │
│        │                                │
│        │ 2a. Delay applied (5s pause)   │
│        ▼                                │
│  [Router Filter]                        │
│        │                                │
└────────┼─────────────────────────────────┘
         │ 2b. Forward to Backend
         ▼
┌─────────────────────────┐
│  Backend Service        │
└───┬─────────────────────┘
    │ 3. HTTP Response
    ▼
┌────────┐
│ Client │
└────────┘
```

**Latency**:
- 50% of requests: ~5000ms (injected delay) + backend processing
- 50% of requests: ~5-50ms (normal)

---

### 3.3 Request Flow with Abort Injection

When an abort policy is applied (e.g., "return 503 for 10% of requests"):

```
┌────────┐
│ Client │
└───┬────┘
    │ 1. HTTP Request
    ▼
┌─────────────────────────────────────────────┐
│  Envoy Gateway                              │
│                                             │
│  [Fault Injection Filter]                   │
│   • Random selection (10% chance)           │
│   • If selected: return 503 immediately     │
│        │                  │                 │
│        │                  │ 2a. Abort       │
│        │                  └─────────┐       │
│        ▼                            │       │
│  [Router Filter]                    │       │
│        │                            │       │
└────────┼────────────────────────────┼───────┘
         │                            │
         │ 2b. Forward (90%)          │ 2c. 503 Response (10%)
         ▼                            ▼
┌─────────────────┐            ┌────────┐
│ Backend Service │            │ Client │
└───┬─────────────┘            └────────┘
    │ 3. Success Response
    ▼
┌────────┐
│ Client │
└────────┘
```

**Outcome**:
- 10% of requests: Immediate 503 error (never reach backend)
- 90% of requests: Normal flow to backend

---

### 3.4 Combined Delay + Abort Flow

When both delay and abort are configured, they are evaluated independently:

```
Request arrives at Envoy
        │
        ▼
┌───────────────────────┐
│ Delay evaluation      │
│ (50% chance)          │
└───┬────────────┬──────┘
    │            │
    │ No delay   │ Delay applied
    │            │ (sleep 5s)
    │            │
    ▼            ▼
┌───────────────────────┐
│ Abort evaluation      │
│ (10% chance)          │
└───┬────────────┬──────┘
    │            │
    │ No abort   │ Abort
    │            │ (return 503)
    ▼            ▼
Forward to      Return 503
Backend         to Client
```

**Possible outcomes**:
- ~45% of requests: No delay, no abort (normal)
- ~45% of requests: Delay only (5s delay, then success)
- ~5% of requests: No delay, abort (immediate 503)
- ~5% of requests: Delay + abort (5s delay, then 503)

## 5. Envoy Filter Chain Placement

### Why Order Matters

The HTTP fault filter **must** be placed **before** the router filter in Envoy's filter chain:

```
Incoming Request
      │
      ▼
┌──────────────────────────────┐
│ envoy.filters.http.fault     │  ← Evaluates fault injection rules
│ • Applies delay if selected  │
│ • Returns abort if selected  │
└──────────────────────────────┘
      │
      │ (If not aborted)
      ▼
┌──────────────────────────────┐
│ envoy.filters.http.router    │  ← Routes to backend
│ • Selects upstream cluster   │
│ • Forwarding logic           │
└──────────────────────────────┘
      │
      ▼
  Backend Service
```

### Rationale

1. **Fault injection must happen before routing**: If the fault filter runs after routing, delays and aborts would not accurately simulate network-level failures.

2. **Abort prevents unnecessary backend calls**: When a request is aborted (e.g., 503 response), it should never reach the backend. Placing the fault filter first ensures aborted requests are short-circuited.

3. **Delay affects total request latency**: Delays should be observed by the client as part of the end-to-end request time, which requires applying them early in the filter chain.

### Complete Filter Chain Example

A typical Envoy listener configuration with fault injection:

```yaml
http_filters:
  # Optional: Header matching for conditional faults
  - name: envoy.filters.http.header_to_metadata
    typed_config: {...}
  
  # Fault injection filter (runs first)
  - name: envoy.filters.http.fault
    typed_config:
      delay:
        fixed_delay: 5s
        percentage: {numerator: 50, denominator: HUNDRED}
      abort:
        http_status: 503
        percentage: {numerator: 10, denominator: HUNDRED}
  
  # Other filters (optional)
  - name: envoy.filters.http.cors
    typed_config: {...}
  
  # Router filter (must be last)
  - name: envoy.filters.http.router
    typed_config: {...}
```

## 6. Safety and Isolation Considerations

### 6.1 Percentage-Based Blast Radius Control

Fault injection uses **probabilistic selection** to limit impact:

- **100% fault injection**: All traffic is affected (use only in isolated test environments)
- **50% fault injection**: Half of requests are affected (moderate chaos testing)
- **1% fault injection**: Minimal impact (safe for production-like environments)

**Implementation**: Envoy uses a pseudorandom number generator to determine whether each request should be affected based on the configured percentage.

**Safety tip**: Always start with a low percentage (e.g., 1%) and gradually increase to validate behavior.

---

### 6.2 Namespace Scoping

All policies are **namespace-scoped**, ensuring isolation:

```
┌─────────────────────────────────────────────────────┐
│ Namespace: staging                                  │
│                                                     │
│  GatewayPolicy: fault-injection-staging             │
│  targetRef:                                         │
│    kind: Gateway                                    │
│    name: staging-gateway  ← Only affects this NS    │
│                                                     │
│  Gateway: staging-gateway                           │
│  HTTPRoute: staging-route                           │
└─────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────┐
│ Namespace: production                               │
│                                                     │
│  No fault injection policy                          │
│  Gateway: production-gateway  ← Unaffected          │
│  HTTPRoute: production-route                        │
└─────────────────────────────────────────────────────┘
```

**Benefit**: Prevents accidental fault injection in production namespaces unless explicitly configured.

---

### 6.3 No Application Code Changes

The architecture achieves fault injection **without modifying backend services**:

```
┌────────────────────┐       ┌────────────────────┐
│ Backend Service    │       │ Backend Service    │
│                    │       │                    │
│ • No SDK required  │       │ • No code changes  │
│ • No library       │       │ • No redeployment  │
│ • Unaware of faults│       │                    │
└────────────────────┘       └────────────────────┘
         ▲                            ▲
         │                            │
         │      Fault injection       │
         │      happens here          │
         │             │              │
         └─────────────┼──────────────┘
                       │
              ┌────────▼────────┐
              │  Envoy Gateway  │
              │  (Fault Filter) │
              └─────────────────┘
```

**Advantage**: Developers can test resilience without instrumenting application code, making it easy to apply across heterogeneous services (Go, Java, Python, etc...).

### 6.4 RBAC and Access Control

Kubernetes RBAC can control who can create or modify fault injection policies:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: fault-injection-admin
  namespace: staging
rules:
- apiGroups: ["gateway.kgateway.io"]
  resources: ["gatewaypolicies"]
  verbs: ["create", "update", "delete", "get", "list"]
```

**Best practice**: Restrict policy creation to platform engineers or SREs to prevent accidental misuse.

## Summary

This architecture provides:

✅ **Declarative configuration**: Fault injection defined as Kubernetes CRDs  
✅ **Zero application changes**: All logic in Envoy's data plane  
✅ **Safe by default**: Percentage-based control and namespace isolation  
✅ **Proven technology**: Leverages Envoy's battle-tested HTTP fault filter  
✅ **Observable**: Metrics and logs available through Envoy's admin interface

The control plane (kgateway controller) translates high-level policies into low-level Envoy configuration, while the data plane (Envoy proxy) performs the actual fault injection with minimal overhead.
